【管理端】支持薪资包发起结算

读不懂原文时先看这页。建议顺序:一句话 → 故事线 → 名词表 → 逐章翻译 → 踩坑清单

一、一句话讲清这个需求

以前「薪资包」只是个算薪用的文件夹,算完就结束了。
这个需求要做的是:让薪资包算完之后能直接发起付款结算,并且把这条链路和「客户端算薪任务」「结算包」「每刻报销」全都串起来。

所以这份文档表面上是 9 个小章节,实际上只有 1 条主线 + 3 块配套改造。

主线

薪资包 → 发起结算 → 生成/绑定结算包 → 流转到财务付款 → 核销 → 回传每刻

3 块配套改造
  • 报销:补贴类费用要能跟着工资一起发(写进国家模板 R1 列),纯报销则单独走报销结算包
  • 付款申请:结算包存的 Bank File 要跟着流转给财务;核销后要发薪资单给员工
  • 数据分析:员工薪资单的字段更名、薪酬周期控件改版、新增「薪资包上传」状态

二、用一条故事线走完整个流程

假设你是 GSR 的薪酬运营,要给客户的约旦员工发 2026-07 的工资。

  1. 每月自动开一个「作业本」系统自动

    系统会在算薪截止日(Cutoff Day)的第二天凌晨 0 点,按「供应商-国家-算薪周期」自动建一个 2026-07 的薪资包。

    作业本里的员工不是随便抓的 —— 只有这个月真的在算薪任务里的员工才进得来。同时系统会把「薪资单ID」和「算薪子任务ID」挂上钩,这样客户端才能看到每个人的算薪结果。

  2. 这张需求只做「导入已有结果」你操作

    点【开始算薪】→ 核对薪资项数据 → 选【导入已有结果】。也就是说,算薪是先在线下算好,再回填进系统。

  3. 点「下载模板」,系统悄悄干了两件事最容易忽略

    不只是给你个文件。它同时在结算中心把「付款结算包-薪资」建好了,状态是「待上传及处理」,并且和薪资包绑在一起。

    分包规则:员工性质、发薪币、结算币、开票币种、发票类型、税率 —— 这 6 项完全一样的员工,合到同一个包里。

  4. 上传四类文件,然后校验你操作

    算薪结果(必传,填在下载的国家模板里,要 A+B 数据)、Payslip 工资单(可选)、Bank File 银行文件(可选,给财务)、其他附件(可选)。单文件最大 80M。

    硬规则:Payslip 是靠文件名最前面的工号认人的,文件名不带工号或写错工号,就匹配不上。

  5. 确认并发起结算 —— 这里挂钩三件事关键动作

    ① 国家模板数据入库,结算包流转到「待业务审核」;② Bank File 存档(后面付款申请要用);③ 把员工的随薪报销单据号挂到对应的付款结算包ID上。

    成功后 toast「发起结算成功」,跳到查看算薪结果页,薪资包状态变成「算薪成功」。

  6. 后面就是付款、核销、回传每刻财务侧

    结算包走到财务 → 发起付款申请(Bank File 一起带上)→ 核销 → 核销后回传每刻,让员工在每刻上看到「已支付」。

  7. 反悔了怎么办?作废例外路径

    二次确认 + 填必填的作废原因。如果已经绑了结算包,得先把它们驳回到「待上传及处理/待创建及确认」才能作废。

    作废后,原本冻结的报销数据、变动信息、假勤数据会一并解冻,下次重建薪资包时重新拉取最新数据。

三、名词速查(看不懂原文八成是卡在这)

名词人话解释
薪资包一次算薪的「作业本」,装着员工名单 + 算薪结果 + Payslip / Bank File 等附件。

报销结算包业务类型 EOR-报销,纯报销的费用单独走它打款。

SPP / SEP结算包 ID 的前缀(示例里 SPP202501160013),不是业务概念,认前缀就行。

四、逐章人话翻译(3.1 ～ 3.9)

3.1 薪资包管理列表 —— 加两个「透视窗」

查询条件加【结算包ID】(精确搜索,多个用英文逗号隔开);列表末尾加【结算包ID】和【结算包状态】两列,多个时用逗号隔开。

状态一共 10 种:待上传及处理 / 待业务审核 / 待补服务费 / 待财务审核 / 已审核 / 待申请付款 / 待财务复核 / 待付款经办 / 待付款核销 / 已完成。

意义:以前从薪资包看不到钱走到哪了,现在一眼能看到。

3.2 创建薪资包 —— 四条改动

  • 自动创建的条件收紧了:必须是 Cutoff Day 次日中国时区 00:00 这个时点才生成;算薪日历的取法是「优先匹配特定月份配置,其次通用配置」。
  • 员工名单收窄:只取「该供应商国家下的员工」∩「该算薪周期 On-Cycle 算薪任务下的员工」。原文的例子很典型 —— 张三虽然在供应商国家名单里,但这个月的算薪任务里没他,就不会被建进薪资包。
  • 新增【薪资包类型】字段(On-Cycle / Off-Cycle,单选必填)。注意:所有历史数据都算 On-Cycle。
  • 查重只查「同服务月份 + 同类型」:On-Cycle 命中 → 报错不允许创建;Off-Cycle 命中 → 提示「请确认是否再次创建」,确认后可以创建。
这段里最绕的内容

3.2 末尾那张表讲的是「报销数据同步」和「每刻回传」。它在文档里出现了两次(3.2 一次、3.3 一次),内容几乎一样。它其实不属于「创建薪资包」,而是发起结算之后的连带逻辑 —— 详见第六节的第 5 条。

3.3 开始算薪 → 核对薪资项 → 导入已有结果 —— 主战场

  • 入口条件:随薪报销列表里如果有异常数据标识,【开始算薪】按钮置灰,走不下去。
  • 下载模板 = 有副作用:生成「付款结算包-薪资」→ 流转「待上传及处理」→ 绑定薪资包 → 导出 结算包ID_国家模板。已经生成过的不重复生成。
  • 四类文件:算薪结果(必传)、Payslip(可选)、Bank File(可选)、其他附件(可选)。
    特例:如果供应商类型是子公司且供应商信息里【是否发送薪资单】= 是,Payslip 上传入口隐藏。
  • 校验失败的样子:格式是 {文件名称}/{结算单ID}:{失败原因},多个原因用逗号隔开。有失败时【确认并发起结算】置灰。
  • 预览统计口径(可拿来直接做断言):x 成功匹配的员工数、y 未成功的,且 x+y = 薪资包员工总数;同理 a+b = 员工总数(Payslip 匹配 / 未匹配);c 是 Bank File 个数、d 是其他文件个数。
发起结算时发生的四件事
  • 结算包逐个上传国家模板,流转「待业务审核」(数据存到新表)
  • 每个结算包存下 Bank File,后续付款申请带给财务
  • Payslip 存到「数据分析-员工薪资单」,并记录生成的薪资单ID。字段映射:子公司名称=当前薪资包供应商名称、薪酬周期=服务月份(如 2026-07 或 2026-08-FH)、状态默认「薪资包上传」
  • 把随薪报销单据号,绑定到该员工对应的付款结算包ID 上

3.4 查看算薪结果

  • 四个页签:Payroll Result / Payslip / Bank File / Others。
  • Payroll Result 有两个维度可切:
    「按结算包维度」—— 只有绑了结算包才显示这个切换按钮,能看到结算包ID、状态、国家模板内容;如果这个包被驳回过,还要显示审核人和审核意见。
    「按员工维度」—— 显示 A/B 部分指标的英文名;不同结算包字段不一样时,取并集,指标编号相同的算同一个薪资项。
  • 重新算薪:会覆盖原结果。先校验所绑结算包状态都是「待上传及处理 / 待创建及确认」;成功后先清空原薪资单附件再更新,原来没传过的员工要新建一条薪资单ID。
  • 下载算薪结果:zip 打包,命名 Payroll Result_供应商名称_国家_服务月份,里面含所有国家模板 + 【Employee Payroll Result】+ 所有 Payslip + Bank File + 其他文件。
  • 3.4.2.3「发起结算」标注了(后续功能规划) —— 这一节目前是空的。

3.5 作废薪资包

二次确认弹窗 + 必填作废原因。若绑了结算包,必须全部处于「待上传及处理 / 待创建及确认」,否则提示「需驳回到待上传及处理状态,系统才可删除掉结算包并作废薪资包」。

通过后:薪资包状态 → 已作废;绑定的结算包被驳回「待创建及确认」并删除、解除绑定;同时解冻三类数据源 —— 报销数据、变动信息(状态名从「待锁定/已锁定」改为「待冻结/已冻结」)、假勤申请数据。

3.6 付款结算 · EOR 类付款

在【待创建及确认】和【待上传及处理】两个 tab 里,凡是从薪资包侧创建的结算包,确认 / 删除 / 上传 / 驳回按钮全部置灰。

原因很简单:这类包的身家性命由薪资包管着,不能在结算侧单独动。

3.7 付款申请

  • 手动发起 / 不合并付款时自动发起 → 结算包的 Bank File 要带到付款申请的【上传供应商提供的材料】字段。
  • 多个结算包合并付款时,如果 Bank File 相同,去重只带一个。
  • 核销完成后,若业务类型是 EOR薪资 / EOR报销 且供应商是 GSR 子公司:原逻辑会生成薪资单发给员工,新逻辑改为从「数据分析-员工薪资单」取附件发给员工。查找链路:付款结算包ID → 薪资包ID → 员工薪资单ID(只取当前付款申请涉及的员工)。

3.8 报销数据 · 已完成 TAB

列表不再显示【系统处理结果】字段。同时新增【同步结果】字段(见第六节第 5 条)。

3.9 数据分析 · 员工薪资单

  • 字段改名:【子公司名称】→【供应商名称】。查询条件、导入 / 查看 / 编辑弹窗同步修改。
  • 供应商可选范围放开:不再限制只有子公司类型,所有供应商都能选。
  • 薪酬周期拆成两个选择框:第一个选年月(如 2026-07),第二个选周期(月度 / 上旬 / 下旬)。选项由所选供应商的合同条款发薪频率决定:
    全是月度 → 第二个框默认「月度」;全是双周 → 「月度」置灰不可选;不一致 → 都能选且无默认值。
  • 状态新增「薪资包上传」选项,查询条件里也要有这个值。

六、读完之后最容易「想当然」的地方

  1. 「下载模板」不是纯下载。它会建结算包、绑薪资包、改状态。所以「重复点会怎样」是个必测点 —— 需求写了「已生成过无需重复生成」。
  2. 触发时点是「次日 00:00」,那当天呢?原文只写了正向,没写当天。当天应当是「不生成」,但这是需要跟产品确认的口径。
  3. Payslip 靠文件名认人。文件名最前面必须是员工在 GSR 的内部工号。而且支持一个员工有多个 Payslip。
  4. 发起结算按钮有两个置灰条件:①随薪报销列表存在异常数据;②导入校验存在失败。这两个是不同环节的闸门,别混成一个用例。
  5. 「一单两包」的拼接顺序是写死的。某报销单据既有报销费用又有补贴费用时,结算包ID 显示为 报销包ID,薪资包ID —— 报销包在前。状态同理。示例:80 元报销 + 20 元补贴 → SPP202501160013,SPP202502090029。
  6. 回传每刻是「两条腿都结清才回传」。
    【EOR-报销】核销后,要确认该单据没有随薪未付费用;【EOR-薪资】核销后,要确认该单据没有纯报销未付费用。
    只结一条就回传 = Bug;两条都结清却重复回传 = 也是 Bug(要幂等)。
  7. 回传每刻有两个前置条件:支付人员工号默认传账号名为 GSR 的工号,而前提是每刻平台上已经创建过这个账号。这条很容易漏测。
  8. 「重新算薪」会清空重建薪资单附件。原来上传过的附件要先清空再更新,原来是空的员工要新建一条薪资单ID。删了没补、或重复建,都是典型缺陷点。
  9. 作废之前必须先处理结算包。状态不对时系统只给提示、不作废。而且作废会连带解冻三类数据源,涉及报销数据、变动信息、假勤三个页面。

  • 3.2 只写「薪资结算包ID」,没带「付款」二字,和 3.3 的「付款结算包-薪资」命名没对齐,存在指代歧义。
